# Placement: arquitectura y servicio desplegado

El servicio `placement` stable/2026.2 SHA `f4a89d3803cb23df22b8714569889ab39c918c34` se analizó en código y en la VM. Placement expone HTTP REST para inventarios, capacidad y consumo. Nova Compute publica resource providers, inventories y traits; Nova Scheduler consulta `GET /allocation_candidates` y reclama recursos con `PUT /allocations/{consumer_uuid}`. El catálogo Keystone anuncia el endpoint de tipo `placement`; el cliente usa token y header `OpenStack-API-Version`. Middleware WSGI de autenticación, política y microversiones precede a los handlers de dominio y SQLAlchemy.

El modelo comprende ResourceProvider (UUID, árbol, generation), Inventory (clase, total, reservas y ratios), Trait, ResourceClass, Allocation (consumer, provider, clase, used) y Consumer (UUID y generation). La DB registra estado y generaciones; una generación obsoleta puede devolver 409. Otros errores relevantes son 400 por petición inválida, 401/403 por auth y 404 por recurso ausente. Se comprobó la existencia de tablas críticas en MySQL; las columnas y constraints se contrastaron con el modelo SQLAlchemy del SHA desplegado.

Secuencia: catálogo y token Keystone → WSGI auth/microversion/policy → handler → objeto de dominio → DB → JSON/status. El servidor anuncia 1.0–1.39. Durante un boot real, el log de Placement registró rutas, status, request IDs, identidad `service nova` y microversiones 1.36, 1.28 y 1.0; el scheduler registró selección de host y reclamación. El baseline capturó también respuestas de providers, inventories, traits, resource classes, candidatos y 404. RF02–RF09 se analizaron para el diseño, sin implementación Go todavía.
