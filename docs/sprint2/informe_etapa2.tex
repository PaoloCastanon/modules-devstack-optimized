\begin{abstract}
Se presenta el análisis verificable de OpenStack Placement y Glance para una reimplementación acotada en Go. Se preparó un laboratorio DevStack reproducible, scripts de verificación y captura, contratos API, modelos de datos y estrategias de compatibilidad. El host disponible no es un servidor dedicado Ubuntu 24.04; por seguridad DevStack no se instaló y no existe aún baseline funcional. El estado del backlog refleja esa limitación.
\end{abstract}

\section{Introducción}
El proyecto compara compatibilidad funcional y, posteriormente, rendimiento y recursos de servicios originales Python frente a implementaciones Go. No se presupone una mejora de rendimiento. La planificación oficial es el libro \texttt{Planificacion\_Trabajo\_Titulo\_OpenStack\_Placement\_Glance.xlsx}, con fecha final de Sprint 2 el 2 de octubre de 2026.

\section{Estado respecto de Etapa 1}
El Excel contiene OE1--OE5, RF01--RF12, RNF01--RNF07 y backlog B01--B26. La Etapa 2 prioriza OE1 (análisis) y OE2 (entorno y baseline). En el repositorio inicial sólo existía un README; se incorporó una copia inalterada del libro y una matriz de requerimientos.

\section{Retroalimentación recibida}
No se encontró retroalimentación formal del profesor guía entre los insumos disponibles. \texttt{feedback-etapa1.md} deja el ítem pendiente para incorporación manual, sin inventar observaciones.

\section{Objetivos del Sprint 2}
OE1 exige arquitectura, APIs, dependencias y flujos críticos de Placement y Glance. OE2 exige OpenStack de un nodo reproducible, smoke tests y baseline original. RF03--RF10 describen implementación posterior; el diseño de esta etapa no los valida.

\section{Entorno experimental}
La auditoría del host registró CachyOS rolling, 16 CPU, 15 GiB RAM, 82 GiB libres, red disponible, virtualización no detectada y sudo no interactivo ausente. Se trata como estación de trabajo. La guía oficial recomienda Ubuntu 24.04 dedicado para DevStack y advierte cambios sustanciales al sistema. Por tanto no se ejecutó \texttt{stack.sh}.

\section{DevStack}
El instalador exige Ubuntu 24.04, usuario no root, declaración de VM dedicada, recursos y red. Fija DevStack \texttt{stable/2026.2} al SHA \texttt{0fb9685c1bf22cd0b4d576d7a74f64195ad934fe}. Usa el grafo de servicios por defecto (Keystone, Nova, Placement, Glance, Neutron, DB y RabbitMQ). Los SHAs y versiones reales de los servicios se registrarán después de instalar; hoy constan como \texttt{UNINSTALLED}. Credenciales van en \texttt{.env} ignorado por Git.

\section{Arquitectura general}
\begin{center}
\fbox{\parbox{0.90\linewidth}{\centering Usuario / OpenStackClient $\rightarrow$ Keystone + Nova API\\
Nova API $\xrightarrow{RPC}$ Nova Scheduler $\xrightarrow{HTTP}$ Placement $\rightarrow$ DB\\
Nova Scheduler $\xrightarrow{RPC}$ Nova Compute $\xrightarrow{HTTP}$ Glance $\rightarrow$ image store\\
Nova / Compute $\xrightarrow{HTTP}$ Neutron}}
\end{center}
Las fuentes Mermaid completas están en \texttt{docs/sprint2/diagrams}. Las rutas HTTP utilizan tokens Keystone; las relaciones internas de Nova usan RPC.

\section{Diseño Placement}
El código upstream \texttt{stable/2026.2}, SHA \texttt{f4a89d3803cb23df22b8714569889ab39c918c34}, muestra handlers WSGI, microversiones, dominio y SQLAlchemy. ResourceProvider publica capacidad, Inventory cuantifica recursos, Trait y ResourceClass describen cualidades/tipos, y Allocation/Consumer registran uso. \texttt{generation} controla concurrencia y puede producir 409 ante actualización obsoleta. Falta validar pipeline y configuración de un proceso instalado.

\section{Diseño Glance}
El código upstream SHA \texttt{8cd693aadc9d5982d9d71b4c34aab4de937ff70c} separa API, dominio, DB de metadata y \texttt{glance\_store} para binarios. El ciclo mínimo es reservar imagen, cargar datos, consultar, modificar metadata, descargar y borrar. El backend real del laboratorio todavía no se conoce; no se supone ruta de filesystem.

\section{Arquitectura objetivo Go}
Se proponen procesos \texttt{cmd/placement} y \texttt{cmd/glance}; paquetes internos API, servicio, modelo y repositorio, más \texttt{glance/store}. Autenticación Keystone, configuración, middleware y logging son compartidos. Handlers negocian HTTP/microversión; servicios resuelven reglas; repositorios manejan transacciones; store transmite bytes.

\section{Estrategia de compatibilidad}
Cada petición se enviará al original y a Go con el mismo estado inicial. Se compararán status, JSON, tipos, campos, headers estables, errores y efectos persistidos. Nova y el cliente OpenStack serán verificadores adicionales. UUID, timestamps, orden no garantizado y request IDs se normalizarán sin ocultar diferencias semánticas. No hay fixtures ejecutadas aún.

\section{Estrategia de pruebas}
Unitarios Go, contrato API, comparación diferencial, integración con Nova y end-to-end de VM forman la pirámide. En la fase posterior se medirán p50/p95/p99 de latencia, throughput, CPU, RAM y errores con carga controlada. No se presentan benchmarks ficticios.

\section{Decisiones técnicas}
Los ADR en \texttt{design-decisions.md} comparan schema original, propio e intermedio. Se propone schema propio Placement compatible por API y metadata Glance acotada con store filesystem único, condicionado a la configuración real. Auth Keystone se conservará. Estas decisiones se revisarán contra el baseline.

\section{Riesgos}
Riesgos: falta de VM, diferencias entre código upstream y despliegue, microversiones negociadas no observadas, almacenamiento Glance real desconocido y retroalimentación formal no recibida. Cada uno tiene verificación pendiente en \texttt{BLOCKERS.md}.

\section{Conclusiones de la etapa}
Quedaron preparados artefactos de diseño y automatización, pero OE1 y OE2 no pueden declararse cumplidos sin contrastar flujos y APIs en DevStack. La ausencia de baseline impide cerrar Sprint 2 de manera verificable. El Excel actualizado reflejará bloqueos y avances parciales.

\section{Próximos pasos Sprint 3}
Primero provisionar la VM y completar B01--B03/B06 y baseline de ambos servicios. Después fijar contratos observados, implementar B07 (providers/inventories), B08 (traits/classes) y B11 (persistencia) con pruebas diferenciales; mantener B20/B25 de Glance en la planificación existente, sin adelantar implementación sin baseline.
