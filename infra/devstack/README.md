# Laboratorio DevStack

Se instala únicamente en VM/servidor Ubuntu 24.04 dedicado. DevStack cambia paquetes, redes y servicios del sistema. `setup-devstack.sh` bloquea otros SO, ejecución como root, ausencia de sudo no interactivo y falta de recursos. `DEDICATED_LAB=YES` es una declaración explícita del operador de que comprobó la dedicación.

La vía automatizada es `make lab-up`: Ansible genera `.env` una sola vez dentro de la VM, ejecuta el instalador con el usuario `stack` y verifica los servicios antes de marcar la instalación como completa. Para instalación manual en otra VM dedicada, copiar `.env.example` a `.env`, establecer secretos alfanuméricos únicos y ejecutar desde raíz `make devstack-setup`. `.env`, `local.conf` generado y logs están fuera de Git. No copiar logs crudos al repositorio porque podrían contener credenciales. `verify-devstack.sh` usa OpenStackClient; si no hay variables `OS_*`, carga el `openrc` de DevStack. `unstack-devstack.sh` detiene servicios; `clean-devstack.sh` exige otra vez `DEDICATED_LAB=YES` y sólo invoca el limpiador de DevStack.

Antes de instalar DevStack, Ansible prepara `root@localhost` de MySQL: convierte `auth_socket` a `caching_sha2_password` usando `DATABASE_PASSWORD` y comprueba `SELECT 1` por TCP a `127.0.0.1` como usuario del sistema `stack`. Conserva `caching_sha2_password` y `mysql_native_password` existentes; una contraseña incorrecta, un plugin inesperado o un error de conexión detienen la preparación. No restablece credenciales existentes. Las credenciales viajan al cliente mediante `MYSQL_PWD` y el SQL por entrada estándar; la tarea usa `no_log` y sólo informa la transición de plugin y el resultado de la prueba. La vía manual requiere disponer previamente de autenticación MySQL compatible.

Las pruebas de esta preparación usan clientes simulados, sin conectar a MySQL ni a la VM: `python3 -m unittest discover -s tests/unit -p 'test_mysql_auth.py' -v` (requiere PyYAML).

`versions.lock` fija los commits de DevStack y Nova. El instalador renderiza `NOVA_BRANCH` con `NOVA_SHA` y, con `RECLONE=no`, rechaza un checkout Nova existente en otra revisión. Al finalizar vuelve a comprobar ese SHA; `record-versions.sh` también rechaza diferencias antes de registrar las versiones. Glance y Placement siguen seleccionados por rama y se registran sus revisiones observadas. La reproducción estricta de todos los proyectos y paquetes secundarios sigue pendiente; no se promete resolver idénticas dependencias en fechas futuras.

### Configuración anterior al pin de Nova

Un laboratorio anterior puede conservar `/opt/stack/devstack/local.conf` con `NOVA_BRANCH=stable/2026.2`. Antes de reintentar manualmente el instalador, comprobar que el checkout de `/opt/stack/nova` coincide con `NOVA_SHA` de `versions.lock`. Si coincide, revisar la configuración y sustituir únicamente el valor de `NOVA_BRANCH` por ese SHA, conservando las credenciales, el propietario y el modo `0600`; no copiar el contenido a Git ni a logs. Si el checkout difiere, detenerse y revisar el despliegue antes de cambiarlo. El instalador compara el archivo completo y rechaza diferencias de configuración; no sobrescribe `local.conf` automáticamente. La reprovisión Ansible con marcador de instalación completa omite el instalador, aunque sigue verificando servicios y la revisión Nova al registrar versiones.
